Auditoria de interface e experiência · Skill analise-ui-ux

Relatório de UI/UX

Projeto: Controle de gastos e verbas (monorepo web + mobile + API)

Data: 2026-10-30
Branch: main @ 0629907
Ambiente: inspeção estática de código (web Next.js 16 / React 19; mobile KMP Compose)
Tipo de inspeção: estática — interface não foi renderizada em navegador nem emulador nesta auditoria
Idioma: Português (Brasil)

1. Resumo executivo

O produto já comunica bem a regra central “alerta, não bloqueio”, tem tokens de tema claro/escuro, máscara BRL cuidadosa e vários padrões de a11y parciais. Porém há fricções objetivas em fluxos principais: aporte mal rotulado no dashboard, login MFA quebrado em subrotas, erros pintados de sucesso, estouro pouco perceptível no lançamento web e mobile sem atalho global de gasto — canal cujo propósito é o lançamento rápido.

Decisões recomendadas agora: corrigir UX-001 a UX-005 (P0) antes de expandir superfície visual; em seguida auth/OAuth/MFA e a11y de Dialog/relatórios (P1). Não redesenhar o sistema visual por estética.

Limitação: conclusões visuais (quebra de layout, contraste percebido em contexto, TalkBack real) têm confiança reduzida. Hipóteses estão marcadas nos achados.

2. Escopo e metodologia

  • Documentos: fundacao-tecnica.md, ADR-007 (gastos/UX), ADR-013 (tema), AGENTS.md, README.
  • Web: rotas em web/src/app, componentes em web/src/components, tokens globals.css, auth.
  • Mobile: shared Compose (VerbasApp, Navigation, Forms, telas), androidApp pontualmente.
  • Heurísticas de Nielsen + usabilidade, IA, a11y (WCAG 2.2 AA como referência, sem declarar conformidade), responsividade, microcopy.
  • Não executado: browser, emulador Android, axe em runtime, Lighthouse, teste com usuários, iOS.
  • Git local preservado; nenhum código alterado; gh auth inválido (issues só após aprovação + reauth).

5. Detalhamento dos achados

UX-001 — "Aportar" no dashboard registra gasto (EXPENSE) em vez de aporte

P0 Severidade: Alta · Esforço: S · Confiança: Alta

Local
Web · Dashboard.tsx:165-166, EnvelopeCard.tsx:80-82, MetasPage passa kind=CONTRIBUTION
Tipo
Usabilidade / Conteúdo
Evidência
No dashboard, EnvelopeCard rotula a ação como "Aportar" para GOAL/SAVINGS_TARGET, mas ExpenseForm é aberto sem kind="CONTRIBUTION". Em MetasPage o kind correto é passado. Avaliação estática do código.
Problema
Usuário acredita estar aportando e pode registrar um gasto na meta.
Impacto
Distorce saldo e propósito da verba; quebra confiança no modelo de metas.
Recomendação
Passar kind="CONTRIBUTION" no Dialog do Dashboard quando a natureza for GOAL ou SAVINGS_TARGET; alinhar título e feedback ("Aporte registrado").
Aceite
  • Botão Aportar no dashboard cria CONTRIBUTION
  • Título e feedback usam linguagem de aporte
  • Teste automatizado cobre o kind enviado
Confiança
Alta — código prova o kind omitido; efeito no backend a validar
Validação
Teste unitário + verificação manual no dashboard e em Metas
Dependências
Nenhuma

UX-002 — Sessão expirada em subrotas não conclui login com MFA

P0 Severidade: Alta · Esforço: M · Confiança: Alta

Local
Web · verbas/page.tsx:11-12 e rotas irmãs; só page.tsx trata mfa-pending
Tipo
Usabilidade / Navegação
Evidência
Subrotas renderizam AuthScreen quando state !== authenticated. Após login com MFA, state vira mfa-pending e a tela permanece AuthScreen sem passo MFA. Avaliação estática.
Problema
Usuário com MFA não consegue reentrar a partir de /verbas, /gastos, etc.
Impacto
Bloqueio de tarefas principais após expiração de sessão.
Recomendação
Centralizar gate de autenticação (layout autenticado) ou tratar mfa-pending/mfa-recovery-setup em todas as rotas protegidas.
Aceite
  • Login com MFA funciona a partir de qualquer rota protegida
  • OAuth disponível onde AuthScreen aparece
Confiança
Alta
Validação
Teste de integração do gate + manual com MFA
Dependências
Possível refactor leve do AuthProvider/layout

UX-004 — Alerta de estouro fraco e sem feedback no momento do lançamento (web)

P0 Severidade: Alta · Esforço: M · Confiança: Alta no código; impacto real é hipótese a validar com uso

Local
Web · EnvelopeCard statusText muted 0.75rem; ExpenseForm sem prévia de saldo; progress clamp a 0 quando negativo
Tipo
Feedback / Visual
Evidência
Status negativo em texto muted pequeno; barra de progresso com value 0 quando isNegative; pós-gasto só "Gasto registrado" sem menção a estouro. Avaliação estática.
Problema
Regra de produto (alerta, sem bloqueio) não é percebida no fluxo principal.
Impacto
Usuário estoura verba sem perceber; viola intenção do ADR-007/fundação.
Recomendação
Pré-visualizar saldo resultante no formulário; feedback pós-registro se isNegative; reforçar visual do alerta (não só cor); barra mostrar excedente ou estado "estourado".
Aceite
  • Prévia ou aviso claro antes/depois do gasto acima do saldo
  • Estado negativo legível sem depender só de cor
  • role=alert mantido
Confiança
Alta no código; impacto real é hipótese a validar com uso
Validação
Teste manual de overspend + teste de componente
Dependências
Contrato de resposta do ledger já expõe isNegative

6. Acessibilidade

  • Pontos fortes web: skip link, lang=pt-BR, aria-current, focus-visible global, prefers-reduced-motion, labels com contexto em cards, teste axe parcial (AuthScreen).
  • Lacunas web: Dialog (foco), erros com role=status e estilo de sucesso, contraste do botão de relatório no dark, title de página fixo, tabs ARIA incompletas em filtros.
  • Lacunas mobile: ícones Unicode, headings/live regions, abas de auth sem selected, progresso negativo pouco descritivo.
  • Não declarar conformidade WCAG sem testes com tecnologias assistivas e contraste em runtime.

7. Consistência visual e padrões reutilizáveis

  • Manter tokens semânticos (--accent, --danger, --purpose-*), tema SYSTEM/LIGHT/DARK e máscara BRL.
  • Problema: CSS duplicado (Dashboard vs Verbas), notices com semânticas conflitantes, cores hardcoded na auth, ausência de primitivos Button/Field/Alert compartilhados.
  • Mobile: TouchTarget 48dp e FormDialog/ConfirmDialog são bons núcleos; alinhar feedback de sucesso e ícones.

8. Plano de melhoria em etapas

  1. Etapa A — P0 (correções de fricção crítica): UX-001, UX-002, UX-003, UX-004, UX-005.
  2. Etapa B — P1 (auth, a11y, confiança): UX-006 a UX-014.
  3. Etapa C — P2 (clareza e consistência): UX-015 a UX-021, UX-023.
  4. Etapa D — P3 / exploração: UX-022; eventual redesign de nav; pesquisa de usabilidade do hábito diário.

9. O que não recomendo mudar agora

  • Paleta teal/coral e tipografia Inter/system — já evitam o “AI aesthetic” genérico e têm ADR de tema.
  • Redesign completo do shell ou troca de design system (MUI etc.) — alto risco, baixo ganho frente às fricções objetivas.
  • Adicionar cache de dados (Redis/React Query) só por “piscar” — preferir stale-while-revalidate local; cache distribuído é fora da política do projeto.
  • iOS polish visual — alvo não validável neste ambiente.
  • Prévia rica de relatórios na web — hipótese de produto (UX-073 do inventário amplo); validar demanda antes.
